1. overview
=================================================================

specs:
  - Lua 5.4 VM with 6M operations per sec
  - 512 KB Memory
  - 16-Bit Display with 128 * 96 resolution
  - 9 buttons per player (which is 2)
  - 4 PCM/BRR Channels
  - 16 MB cassette slot
  - Unlimited Flashrom for saving

2. a deep dive into each aspect
==========================================================================

cpu:
	the console includes the Lua 5.4 VM cpu with a 6 MIPS limit and a few more opcodes.
	it's locked at 60hz and comes with fault protection, halting the execution if it spots
	any error in the code.
	
	the cpu is the only way you can manipulate the memory, with it providing raw block 
	operations like peek(), poke(), memset(), memcpy(), and reload().
	
	the virtual execution thread does not run a continuous procedural top-down line 
	of code. instead, the cpu calls two vectors during execution, one on startup and one on every frame. 
	
	the one on startup is called _boot(). while not needed, it can be used to intitalize variables
	and run startup functions
	
	the one called every frame is called _tick(). this is crucial and is triggered 60 times a second. 
	it can read input registers, handle game loops, moving sprites around, and many more.
	
	dev's diary: any code not within these two vectors will not run, meaning any variables or functions 
	must be nested within or used by the _tick() vector in some way, shape, or form. and leaving out
    the _tick() vector in a cassette will result and a infinite boot state. causing a softlock.
	
memory:
	the console maps out a continuous 512 KB linear physical memory block ranging from 0x00000u to 0x7FFFFu.
	literally everything is memory mapped, meaning graphics pipelines, audio units, and registers react 
	purely to raw bus reads and writes.
	
	lets take a look at it again and break down is usually inside each block:
		0x00000u-0x05FFFu  	VRAM Framebuffer (128x96, 24KB)
		0x06000u-0x06400u  	Palette RAM (512 slots, 1KB)
		0x06440u-0x0644Fu  	Input State Registers
		0x06450u-0x065FFu  	SPU Audio Registers
		0x06600u-0x068FFu  	BIOS Font (Packed 1-bit, 5x5 Matrix)
		0x06900u-0x0E8FFu  	Sprite Bank 0 & 1 (16KB each)
		0x0E900u-0x1E8FFu  	SPU Soundbank RAM (64KB)
		0x1E900u-0x3E8FFu  	Tilemap Data Block (128KB)
		0x3E900u-0x7DFFFu 	Cartridge RAM (~256KB)
		0x7E000u-0x7FFFFu  	SRAM Flash Save RAM (8KB)
	
	framebuffer (24KB):
	the framebuffer is what gets outputted to the screen. each pixel has 2 bytes and that has the raw rgb value.
	so what would that look like in practice would be:
		poke((0x00000 + (24 * 128 + 13) * 2), 0xFFFF) -- pokes the 16 bit value to the framebuffer and offsets 
		it to (13, 24) with 128 being the width of the screen.
	it will lead to a white pixel at that exact spot! (we'll get more in depth with the primitives in 3.2)
	
	palette (1KB):
	the palette ram is basically where the game's color entries gets stored. this indirectly comes with the benefits
	of the palette swapping and saving space all together! the bios already has 16 colors loaded into ram automatically
	with it starting at 0. you can add your own 16-bit color by doing:
		poke((0x06000 + (16 * 2)), 0x194A) -- poke the darkblue color to slot 16. the primitive functions handles the 
		indexing of the palette, but isn't too hard to set it up yourselves.	
	dev's diary: you can indeed override default 16 slots but you cannot leave the palette ram blank unless you enter
	a raw rgb value. the primitive functions like map() and sprite() depend on these slots heavily to render. so yeah,
	happy palette swapping!

	bios font (768B):
	the bios also loads its font into the allocated ram block. the primitive function to print onto the screen, text(),
	is pretty straight forward as well. now if you want to change the font, it has to be in a certain format before you 
	upload. you see, the bios font is a 1-bit, 5x5 matrix. so each character is 5x5, but also takes up 6 bytes of RAM.
	heres a visualization:
		Row 0:  . # # # .   --> Bits: 01110b --> Hex: 0x0Eu
		Row 1:  # . . . #   --> Bits: 10001b --> Hex: 0x11u
		Row 2:  # # # # #   --> Bits: 11111b --> Hex: 0x1Fu
		Row 3:  # . . . #   --> Bits: 10001b --> Hex: 0x11u
		Row 4:  # . . . #   --> Bits: 10001b --> Hex: 0x11u
		Row 5:  [PADDING]   --> Bits: 00000b --> Hex: 0x00u
	if you want to swap out the font, you can do:
		reload("assets/widesquat.bin", 0x06600) -- swap out the bios font with another font in a similar format
	dev's diary: if you just want to edit a single character you can use the char target method with poking the character's
	base (0x06600u + (ascii - 32) * 6) and going row by row. (6 in total)

	sprite banks (16KB, 2 in total):
	the sprite banks are 128 x 128 in width and height and contain raw indexes in RAM, meaning they contain no rgb data by 
	itself. to load the raw indexed spritesheet into a bank, do:
		reload("assets/sprites.raw", 0x06900) -- to load sprites into sprite bank 0
		-- or --
		reload("assets/sprites.raw", 0x0A900) -- to load sprites into sprite bank 1 (highly recommended for tiles)
	dev's diary: our sprite() primitive automatically indexes our sprites into 8x8 sprites, with the ability to change the width 
	and height with the extra parameters. to make the sprite() primitive reference the other sprite bank. switch banks by doing 
	poke(0x06409, 1). you can switch back to sprite bank 0 by doing poke(0x06409, 0). and yes, you can render sprites from both 
	banks.
